# GUI 与可选导航架构草案

状态：**部分实施**。基于 2026-09-23 的本地仓库与本轮 GUI/导航讨论；G0/G1 的库存总览首批功能
已落地，容器地图与导航章节仍是提案。
实施顺序与验收门见 [分阶段计划](gui-navigation-implementation-plan.md)。现有 Core v1 的实际能力与限制以
[Core v1](core-v1.md) 和代码为准。

## 1. 现状与设计边界

| 范围 | 仓库现状 | 本文提案 |
| --- | --- | --- |
| 索引 | 已采集玩家打开过的支持容器及玩家背包，按 scope 保存最新快照；可搜索物品、variant、数量和来源 | 为全量列表、容器地图补只读展示查询 |
| 客户端展示 | `ItemFinderClientApi` 已提供查询；紧凑库存总览、会话级数量草稿与设置页已实现 | 精确 variant 来源分配、全屏容器地图、局部 3D |
| 取物规划 | `core.planner.RoutePlanner` 按同 scope、同维度的容器**直线距离**做确定性最近邻，报告缺货 | 将停靠点交给可选导航服务，按真实可通行路线估算与展示 |
| 导航 | 没有通行方块缓存、轨迹学习、A*/Dijkstra、跨维度和载具交通实现 | 可独立运行的导航模块或 Mod，经可选接口接入 LItemFinder |

`RoutePlanner` 里的“路线”目前仅是取物停靠顺序。它不证明两点之间可达，也不提供实际行进路径。
正式 UI 不应把 `totalDistance()` 标成导航距离或预计时间。现有 Alpha 的 M5 兼容和打包验收仍按
[现有计划](next-phase-neoforge-1.21.1.md) 独立完成。

## 2. 界面信息结构

首期主界面采用完整 Screen：`库存总览 / 获取计划 / 容器地图 / 设置`。搜索作为总览和地图的共同过滤器，
不要求先制作单独的搜索页。整体视觉参考 Litematica 材料列表的紧凑密度；容器地图是 WorldMap 式
全屏平移、缩放界面。简洁风格指低噪声、明确层级，不表示将主功能拆成多个悬浮窗。

### 2.1 库存总览

- 每行显示物品图标、名称、**已记录总数**及必要的来源/更新时间提示；按总数降序，平局按稳定物品 ID
  和 variant 排序。列表行紧凑、可滚动；搜索、分组或维度过滤不改变数量语义。
- 默认按注册表物品 ID 聚合；不同 Data Components variant 的合计可以展示，但展开后应列出 variant
  及其各自来源。特定 variant 的需求必须按完整 `ItemKey` 分配，不能把不同附魔、药水等直接互换。
- “已记录”是最后一次观测到的快照，不保证容器当前仍有该数量。玩家背包、末影箱等无坐标来源参与
  总览，但地图在单独的“逻辑容器”区展示；嵌套物品使用根容器位置与完整 `ContainerPath`。
- 只有点击物品行才展开获取数量编辑。行内展开区明确给出 `− [纯整数输入框] +`、加入/移出计划操作
  和上限提示；不把左键、右键隐式分配成两个核心操作。按钮默认每次增减 **64 个**。
- 整数输入接受十进制非负整数，禁止小数、负数、溢出；提交时限制在 `0..可分配已记录数量`。零代表
  从计划移除。索引变化时重新计算上限并提示被收缩的需求，不能静默制造超额取物计划。
- 鼠标滚轮停在“盒 / 组 / 个”的对应数值上时，分别按 `27 × S / S / 1` 增减；`S` 是客户端注册表给出
  的该物品最大堆叠数（典型为 64，也可能为 16 或 1）。盒仅是 27 格换算单位，不暗示玩家拥有潜影盒。
  未确认 `S` 时仅提供纯整数输入与个数增减，不猜测组/盒换算。所有操作统一应用上限与零下限。
- 普通展示默认为**纯数字**。编辑区默认用投影材料列表式分解 `a 盒 + b 组 + c 个`；若只显示组数，
  使用 `q 组 + r 个` 的整数尾数，绝不显示小数组数。显示模式仅在设置页配置，行内不设临时切换。
  设置分别控制普通展示和编辑展示，默认值如上；数值底层始终保存整数个数。
- 对大列表以分页/虚拟滚动和稳定排序生成不可变展示数据。图标与物品名称在客户端线程解析；聚合和
  排序不在每一帧重复运行。状态变更或 scope 切换时刷新。

### 2.2 获取计划

获取计划保存“要取什么、多少、当前从哪些来源分配”，并标明缺货、过期快照和待确认前置任务。
同一份已记录库存同时用于普通取物和载具准备时，必须共用预留账本：每个精确物品来源的可用量只
能分配一次。加入计划本身不点击容器，也不自动消耗材料。

### 2.3 容器地图

- 地图占据主屏幕，可平移、缩放；顶部放搜索、scope/维度/分组/容器类型筛选，右侧为选中容器详情。
  全局 2D 以真实 `x/z` 坐标显示**已记录、有坐标**的容器，远距聚合点位，近距展开单点。
- 当前数据库只有容器快照，没有世界地形图。首版以坐标网格、容器点、聚合簇和玩家位置构成地图；
  不把未观察区块绘制成已知地形。选中点显示坐标（含 Y）、最后观测时间、容器类型、匹配数量、
  嵌套路径和内容预览。空容器也应可见，因此需要按根容器列举的只读接口，不能只反推物品搜索结果。
- 玩家背包、末影箱以及会话级无可靠坐标来源放入侧栏“逻辑/未定位容器”；不能伪造地图点。
- 局部 3D 重点解决上下层辨识：保持真实 `x/y/z` 相对位置，提供旋转、缩放、Y 层切片和楼层标签；
  容器标记与路线入口高亮。没有经过观察的建筑方块不渲染成可靠结构；可先用楼层网格和简化线框。
- 从总览物品进入地图时高亮来源容器；从计划进入时显示停靠顺序。导航服务可用时叠加分交通方式的
  实际行进路线、维度切换点和置信度。服务缺席或路径未求得时只显示停靠点与**示意连接线**，明确
  标注其不可作为可走路线。不同维度分别显示地图层，并以已知传送连接串联行程。

### 2.4 展示层数据边界

Screen 只消费不可变 view model，不直接持有正在变化的菜单、`ItemStack` 或 SQLite 连接。现有
`ItemFinderClientApi.search(SearchQuery.all())` 可支持首个非空物品列表，但不足以提供空根容器、
地图摘要、增量刷新和计划预留。后续只读扩展建议包含：

```text
InventoryOverviewPage(scope, revision, rows, nextCursor)
ContainerMapPage(scope, dimension, bounds, roots, nextCursor)
ContainerDetails(rootId, observedAt, entries, nestedPaths)
```

接口以索引的稳定快照和 revision 为边界，切换 scope 后旧页面结果作废。`clearCurrentScopeData()`
仍由 UI 显式二次确认。物品显示名、图标、最大堆叠数在 Loader 层解析，Core 保持与 Minecraft 解耦。

## 3. 可独立导航服务

导航先以独立模块设计：未来可拆成单独 Mod；LItemFinder 仅持有极小的可选 provider 接口，缺席时
所有库存、搜索、地图点位及取物计划照常可用。导航自身可接受普通航点，不要求安装 LItemFinder。
建议依赖方向：

```text
LItemFinder 库存/GUI ──可选请求──> NavigationProvider
                                      │
                         navigation-core（纯领域与搜索）
                                      │
                         navigation-neoforge（观测与渲染适配）
```

`navigation-neoforge` 依赖 `navigation-core`；库存 Core 不反向依赖任何导航实现。

可选接口只交换 scope、维度、坐标、航点、玩家能力/载具状态、路径偏好、只读库存候选与结果，不导出
LItemFinder 的数据库对象。结果明确区分 `FOUND / PARTIAL / UNKNOWN / UNREACHABLE`，并返回路径段、
交通方式、预计时间/代价、数据新鲜度、证据来源及待确认前置任务。若最终独立发布，以稳定接口和
版本协商替换模块内调用；LItemFinder 的构建、启动和测试不得依赖导航 JAR。

### 3.1 三层数据

1. **世界通行数据缓存**：按 scope、维度和区块/空间块保存从客户端实际加载世界观察到的通行面、
   高差、危险/障碍及交通设施状态。缓存稀疏、有版本和观测时间，并限制大小；方块变化、区块重载
   或设施状态变化使相关区域失效。不扫描未加载区块，也不从容器索引推断道路。未知区域保持未知。
2. **导航拓扑图**：节点代表区域入口、传送门、车站、码头、冰道端点、换乘点与目标；边含交通方式、
   可用条件、方向、设施状态、行程时间和置信度。跨维度连接必须由实际观测或可信适配器证据建立；
   坐标比例只可作候选线索，不等于已验证的传送门出口。
3. **玩家轨迹学习**：记录玩家实际经过的连接、用时和交通方式，用于发现设施、校准速度和加速搜索。
   轨迹属于证据与缓存，不能限定候选边；即使没有旧轨迹，也要主动搜索已知通行数据里的新捷径。
   轨迹按 scope 隔离，并提供清除与关闭记录的设置。

### 3.2 搜索与成本

- 局部步行在已知通行面上用 A* 求可行路径；高差、跳跃/游泳能力、碰撞与危险规则进入边可用性。
  拓扑图与多交通方式的**非负预计时间成本**用 Dijkstra 求最短路；有可证明不高估的启发式时可用 A*。
  跨维度/传送边难以保证欧氏距离启发式安全时退化为零启发式，即 Dijkstra。
- 每段成本包含行进时间、上下载具/换乘、开启或等待设施、风险偏好和准备任务时间。不同目标可在
  “最快 / 少换乘 / 步行优先”等策略下分别重算；风险若不可接受则作为禁用条件而非负权重。
- 步行、冰道船、水路船、铁路先纳入模式模型；鞘翅与模组交通通过能力和边提供者扩展。道路速度
  随玩家能力、药水/装备、载具、环境及设施状态变化，不以固定方块距离代替时间。未知或失效设施
  不直接当作可用捷径。
- 局部路径和模式边按需生成、验证与缓存；搜索允许连接过去未走过但当前已知可通行的区域。预算
  耗尽或需要穿过未知区域时返回 `PARTIAL/UNKNOWN`，展示已证实部分和缺口，不输出虚假的完整路线。
- 多容器取物另有选点与访问顺序问题。第一版可复用现有 `RoutePlanner` 生成候选停靠点，再按导航
  时间重新评估顺序；局部最短路径不保证多站全局最优。后续用有界优化改进多站方案，报告成本与
  近似性质，不宣称当前最近邻已求得全局最短。

### 3.3 载具准备与资源预留

默认策略允许**推荐**取载具或合成载具的前置任务，但必须在 GUI 中由玩家确认后才并入计划；
推荐本身不进行自动取物、合成或导航执行。规划器比较“已有载具”“去已记录容器取”“可制作”与
“无需载具”方案时，应计入准备时间、材料、当前玩家背包和预计路线收益。

前置任务组成有向无环依赖图。使用 `scope + 精确 ItemKey + 来源/槽位 + 数量` 的共享预留账本，
将载具材料和最终获取需求统一分配；同一份库存不得分给两个任务。递归展开时保留访问栈检测循环，
设深度与任务数上限；循环、缺料或来源过期时给出阻断原因和可选替代路线，不递归生成无限任务。
玩家能力或载具状态变化、容器快照更新、交通设施失效后，先撤销受影响预留并重算，再请玩家确认
变化后的计划。合成配方必须由实际可用的配方数据提供，不能凭物品名推断。

## 4. 约束与尚待验证的决策

- 客户端只读观察遵守现有“玩家访问过的容器、已加载世界数据”边界；导航缓存与容器索引分开存储、
  分 scope 隔离，并可分别清理。世界通行缓存的存储量与更新开销需原型测量后定配额。
- 地图背景是否接入第三方地图 Mod、如何获取模组交通的可信设施状态，属于后续兼容性决策；首版
  坐标地图和导航接口不依赖第三方地图。
- 是否将导航从同仓模块拆到单独仓库/Mod，在接口和独立航点用例通过验收后决定；拆分不改变库存
  功能的运行依赖边界。
